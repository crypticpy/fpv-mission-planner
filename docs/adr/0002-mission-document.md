# 0002 — MissionDocumentV1 is the authoritative mission state

**Status**: Accepted (2026-07-30)

## Decision

A mission is an **immutable, versioned, persisted document** —
`MissionDocumentV1` — independent of any renderer. Shape (frozen contract;
field-level schema lives in `src/domain/mission/mission-schema.js` once built):

```text
schemaVersion            1
id, title, createdAt, updatedAt
launch { latitude, longitude, elevationMslM }
aircraftSnapshot         embedded copy, not a catalog reference
batterySnapshot          embedded copy incl. pack-instance overlay
payloadSnapshot
environmentReference     how weather is sourced (live | preset | manual) + values
route {
  waypoints[]            { id, latitude, longitude }
  segments[]             { id, from, to, altitude { authored, reference, resolvedMslM },
                           speedPolicy, intent, holdS?, subjectRef?, camera?, overrides? }
  returnPolicy
}
planningPolicy { reserve, gustFactor, windLevel, radioBand }
scene { subjects[], cameraProfile }
provenance
```

Rules:

- **Stable identifiers** on missions, waypoints, segments, constraints,
  subjects, and scene elements. Prefix + random suffix (`msn_`, `wpt_`, `seg_`,
  `con_`, `sub_`), generated by an injectable id source so tests are
  deterministic. IDs never change across edits; deleting and re-adding creates
  a new ID.
- **Snapshots, not references.** The document embeds copies of the aircraft,
  battery, payload, and environment at authoring time. Catalog edits never
  silently change a saved mission; a "re-sync from catalog" action is an
  explicit command that bumps `updatedAt`.
- **Derived values are never stored in the document.** Energy, time, clearance,
  warnings, radio results live only in the separately versioned
  `AnalysisSnapshot` (ADR 0007-adjacent contract, built in M2) and can always
  be recomputed.
- **All edits go through commands and a reducer**
  (`mission-reducer.js`): `(document, command) → new document`. Pure, no I/O.
  Renderers and adapters never mutate the document.
- **Migrations are forward-only**, one step per schema version, each with
  round-trip fixtures. Unknown future versions are rejected with a readable
  error, never partially loaded. Corrupt or incomplete records fail safely to
  "not loaded", never to a half-mission.

## Why

Versioning, undo, saved missions, export, 3D rendering, and agent ownership all
become ambiguous while mission state lives inside the mutable UI state object
and the map owns the route. One authoritative document with one mutation path
makes every consumer (map, planner, brief, exporters) a reader of the same
truth.

## Consequences

- M1 moves route ownership out of `map.js`; "moving launch clears the route"
  becomes an explicit domain command with predictable coordinate behavior.
- The current mutable `state.js` splits into mission document, computed
  (analysis) state, and UI preference state.
- Share/import (`schema.js`) becomes an adapter over the document rather than
  a parallel source of truth.
