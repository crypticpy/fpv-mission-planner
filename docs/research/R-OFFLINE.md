# R-OFFLINE — Offline Persistence Failure-Mode Matrix

Research for the planned move of mission documents and forecast/terrain evidence
snapshots from `localStorage` (see `js/store.js`) into IndexedDB, with
`localStorage` kept only for small prefs (map view, theme, session flags).
FPV is a hand-rolled-`sw.js` PWA (see `sw.js`) used in the field, often with
degraded or no connectivity — this matrix is the set of storage/SW failure
modes the persistence design must survive, not a general storage tutorial.

All claims below are sourced to MDN, web.dev, or webkit.org, with the date
each source was accessed (2026-07-30) and, where the source exposes it, the
page's own last-modified date. Where two primary sources disagree, both are
quoted and the more recently-updated one is flagged as authoritative.

## 1. Failure-mode matrix

| # | Failure mode | Which browsers | How to detect it | Required design response |
|---|---|---|---|---|
| F1 | `IndexedDB` write throws `QuotaExceededError` mid-transaction | All (Chrome/Edge, Firefox, Safari) once the origin's bucket is full | `try/catch` around `IDBRequest.onerror` / awaited wrapper rejecting with `event.target.error.name === 'QuotaExceededError'` | Every IDB write path must catch this explicitly (not just swallow-all like today's `store.js`), surface a "storage full" state to the UI, and offer a manual export/prune path *before* the write is retried. Never let a failed transaction silently drop a mission document. |
| F2 | `localStorage.setItem` throws `QuotaExceededError` (5–10 MiB/origin cap, shared with sessionStorage) | All | Same `try/catch` pattern already in `js/store.js` (`set()` swallows it) | Confirmed the existing swallow-and-continue behavior in `store.js` is correct *for prefs*, but is exactly why mission documents must not live there — a full 5–10 MiB quota is trivial to hit with flight logs/photos. |
| F3 | Origin evicted wholesale under storage pressure (LRU) | Chrome/Edge, Firefox, Safari — all use an LRU-by-origin policy for "best-effort" (non-persisted) storage | `navigator.storage.estimate()` usage creeping toward quota; app relaunch finds IndexedDB empty/recreated | Call `navigator.storage.persist()` (see §2) so the origin is opted out of LRU eviction; still design for the case persistence is refused — treat IndexedDB as a *cache of record with export*, not the only copy of a mission plan. |
| F4 | Safari: all script-writable storage (IndexedDB, localStorage, Cache API, SW registration) wiped after 7 days of no user interaction with the site, under ITP | Safari/WebKit only (desktop Safari, iOS/iPadOS Safari) — **does not apply** if the app has been added to the Home Screen (see §2) | No event fires; data is just gone on next launch. Detect via a version/heartbeat record read-back at startup. | This is the single biggest offline-reliability risk for a field tool used sporadically. Design response: (a) push users toward "Add to Home Screen" in onboarding/README, since that exempts the origin from the 7-day timer and gives it the full browser-app quota; (b) never treat IndexedDB as durable across long gaps for users who stayed in Safari-the-browser; (c) ship an explicit export/backup affordance (see §4) so a wipe is recoverable. |
| F5 | Safari (older, pre-macOS 14/iOS 17): tiny initial quota (~1 GB) with a permission prompt to exceed it | Safari, legacy versions | `navigator.storage.estimate()` showing quota near 1 GB; `QuotaExceededError` far earlier than Chrome/Firefox | Keep per-record payloads small (terrain/forecast snapshots should be pruned/bounded, not accumulated forever); don't assume Chrome-sized quotas. |
| F6 | Firefox (pre-115, released 2023-07-04): `indexedDB.open()` rejects with `InvalidStateError` in Private Browsing | Firefox only, and only on very old versions still in the field | `open()` request's `onerror` fires synchronously with that error name | Firefox 115+ now supports IndexedDB in Private Browsing via encrypted on-disk storage purged at session end (see §2) — but a private-mode session on any browser is still transient by design; app must not assume a private-mode IndexedDB write survives the session, and should fail soft into an in-memory/localStorage-prefs-only mode rather than throwing an unhandled rejection. |
| F7 | Partial failure of `cache.addAll()` during SW `install` | All — this is spec behavior, not a bug | The `install` event's `waitUntil()` promise rejects; SW install fails and the *old* SW (if any) stays in control | `cache.addAll()` is atomic: if any one precache URL 404s or the fetch fails, **none** of the URLs are written to that cache (confirmed against current `sw.js`, which already relies on this — a bad entry in `PRECACHE_URLS` fails the whole install, leaving the previous cache/SW active rather than half-precaching). Keep this atomicity; do not switch to per-file `cache.put()` loops that could leave a half-populated app shell. |
| F8 | Stale service worker never updates because the browser served the SW script itself from HTTP cache | All | App keeps running old code after a deploy; `navigator.serviceWorker.getRegistration()` shows old script date | Browsers now bypass HTTP cache for the SW script fetch itself if the last check was >24h ago (regardless of `Cache-Control`), and Chrome ≥68 defaults `updateViaCache` to `imports` (i.e., the top-level SW script is *never* served from HTTP cache on update-check, only `importScripts()` resources are). `sw.js` doesn't set `updateViaCache` explicitly today, so it already gets this default — no change needed, but document it so a future refactor doesn't accidentally set `updateViaCache: 'all'` and reintroduce the stale-script problem. |
| F9 | New SW stuck in `waiting` because old SW still controls open tabs (mission in progress) | All | `registration.waiting` is non-null; UI never gets the new app-shell version | Current `sw.js` calls `self.skipWaiting()` unconditionally on install and `clients.claim()` on activate — appropriate for a no-login, no-server-session app, but means an in-flight mission session in another tab can suddenly be handed to new JS mid-use. Recommendation: keep `skipWaiting`/`clients.claim` (matches the "always run the latest deploy" design already documented in `sw.js`'s own header comment), but any IndexedDB *schema* migration triggered by the new SW/app version must be additive/backward-compatible for the brief window where an old tab and new tab may both be alive. |
| F10 | IndexedDB transaction auto-commits earlier than expected because code awaited something outside the transaction | All (spec behavior) | `TransactionInactiveError` thrown on a request made after an `await` | A transaction commits once its microtask/request queue drains and control returns to the event loop — if code does `await fetch(...)` or any non-IDB promise *inside* a transaction, the transaction is already closed by the time execution resumes. Repository code must gather all data first, then open the transaction and fire all IDB requests synchronously within it, never `await` a non-IDB promise mid-transaction. |
| F11 | Data "committed" (per `oncomplete`) is lost anyway on OS crash/power loss | All, more likely on Firefox 40+/Safari/Chrome ≥121 | No detection possible from script; only shows up as a missing record after a crash | Both `'strict'` and `'relaxed'` durability only bound *when* the browser considers the transaction done, not whether the OS actually flushed to disk before a crash — `'strict'` still doesn't guarantee zero data loss on power failure, it just narrows the window. Chrome changed its **default** from `strict` to `relaxed` in Chrome 121 (Nov 2023) to match Firefox/Safari's long-standing relaxed-by-default behavior. Design response: request `durability: 'strict'` only for the specific writes where losing the last few seconds matters (e.g., finalizing a completed flight log entry), and treat everything else as best-effort — this is a performance/durability trade the repository API should expose explicitly, not hide. |
| F12 | Structured-clone limits reject a write silently-ish (`DataCloneError`) | All (spec behavior) | Synchronous throw from `IDBObjectStore.add/put`, not an async request error | Functions and live DOM nodes cannot be cloned into IndexedDB. Mission documents/forecast snapshots must be plain serializable data (objects, arrays, typed arrays/`ArrayBuffer`, `Blob`, `Date`, `Map`, `Set` are all fine) before they reach the repository layer — never pass a Leaflet layer object, a DOM element, or a function reference into a store. |
| F13 | `navigator.storage.persist()` silently denied, or not called at all | Firefox (prompts user, who can decline); any browser where auto-grant heuristics aren't met | `persisted()` returns `false` after calling `persist()` | Chrome/Edge auto-grant based on engagement heuristics (bookmarked, high site-engagement score, installed as PWA, notification permission) with no user-visible prompt; Firefox shows an explicit permission popup the user can dismiss/deny; Safari's own quota/eviction system for installed Home Screen apps makes `persist()` largely moot there (see §2). Because grant is never guaranteed, the design must treat persistence as a *hardening* measure, not a precondition for correctness — the export/backup path (§4) is the actual guarantee. |
| F14 | Cache Storage API entries evicted even though the origin called `persist()` and it was granted | None currently documented as a normal-path behavior for a genuinely persisted origin | N/A in practice | A persisted origin's IndexedDB and Cache Storage share one eviction unit (the origin's storage bucket) — the browser does not selectively evict one cache within a persisted origin while sparing IndexedDB, or vice versa. If eviction happens, it takes everything for that origin at once. This is actually good news for the design: there's no scenario to guard against where the app shell cache survives but mission data doesn't (or vice versa) *within the same persistence tier* — but it also means losing persistence loses everything, reinforcing F13's export requirement. |
| F15 | Private-Browsing / Incognito storage is memory-backed or capped far below normal quota, then vanishes at session end | Chrome Incognito (quota reduced to roughly 5% of disk, or a small fixed cap with "clear cookies on close" style settings); Firefox Private Browsing (now disk-backed but encrypted-and-purged at session end, Firefox 115+); Safari Private Browsing | Small `navigator.storage.estimate().quota`; all data gone after the private window closes — no error, just absence | The app cannot detect "am I in private mode" reliably or portably. Treat this as a normal-but-ephemeral session: don't warn users they're in a special mode (no reliable way to know), but the export/backup affordance in §4 is the only mitigation, since anything not exported before the private window closes is gone. |

## 2. Claims sourced

**Storage quotas (per browser, current)**
- MDN, *Storage quotas and eviction criteria* — https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria — page last modified 2026-01-05 per `mdn/content` git history (accessed 2026-07-30). Chrome/Edge: 60% of total disk per origin group, both best-effort and persistent, overall browser cap 80% of disk (LRU eviction of best-effort origins above that). Firefox: best-effort is `min(10% of disk, 10 GiB)` per eTLD+1 group; persistent mode up to 50% of disk capped at 8 TiB, not subject to the group limit. Safari (macOS 14 / iOS 17 and later): ~60% of disk for browser-app origins (and for any site added to the Home Screen/Dock, which gets treated as a "browser app" for quota purposes), ~15% for non-browser embedded WebViews, ~1/10 of parent quota for cross-origin iframes; overall caps 80% (browser) / 20% (non-browser) of disk. Legacy Safari (pre-2023): ~1 GiB initial per-origin quota with a user prompt to exceed it.
- web.dev, *Storage for the web* — https://web.dev/articles/storage-for-the-web — last updated 2024-09-23 (accessed 2026-07-30). Gives Chrome 80%/60% (consistent with MDN above), Firefox "up to 50% of free disk" with a **2 GB** per-eTLD+1 group limit (older figure than MDN's 10 GiB — MDN is the more recently updated source, treat 10 GiB as current), Safari "~1 GB" desktop/mobile growing in 200 MB increments (this describes the pre-2023 legacy behavior; superseded by the WebKit 2023-08-10 policy below for current Safari/iOS). Chrome Incognito: ~5% of disk, or ~300 MB with "clear cookies on close" enabled.
- WebKit blog, *Updates to Storage Policy* — https://webkit.org/blog/14403/updates-to-storage-policy/ — published 2023-08-10 (accessed 2026-07-30). Describes the current (Safari 17+) per-origin/overall quota tiers by app type quoted above, confirms Home Screen web apps get the same quota tier as the Safari browser app, and states eviction is LRU-by-origin based on "the time of the last user interaction, or the time of the last storage operation," and applies to localStorage, IndexedDB, Cache API, Service Worker, and File System APIs — but **not** cookies or the HTTP cache.

**QuotaExceededError behavior across storage types**
- MDN, *Storage quotas and eviction criteria* (as above): IndexedDB and Cache API writes throw `QuotaExceededError`, must be handled with try/catch; localStorage throws the same error name at its 5–10 MiB (Web Storage, `localStorage` + `sessionStorage` combined) per-origin cap. When an origin is evicted, all of its storage types (IndexedDB, Cache API, etc.) are deleted together, atomically, specifically to avoid inter-store inconsistency.

**persist() / persisted()**
- MDN, *StorageManager: persist() method* — https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist — last modified 2024-07-26 (accessed 2026-07-30). `persist()` returns a `Promise<boolean>`; "the browser may or may not honor the request, depending on browser-specific rules"; requires a secure context (HTTPS); not available inside Web Workers.
- web.dev, *Persistent storage* — https://web.dev/articles/persistent-storage — last updated 2020-05-12 (accessed 2026-07-30; older source, heuristics described are directionally still accurate but not re-verified against 2026 browser behavior). Chrome/Chromium auto-grants based on engagement heuristics (site engagement score, bookmarked/installed, notification permission granted) with no visible prompt. Firefox shows an explicit user-facing permission popup. Browser support noted from Chrome 55+/Edge 79+/Firefox 57+/Safari 15.2+.
- WebKit blog, *Updates to Storage Policy* (as above): confirms an origin in **persistent** mode is exempt from LRU/pressure eviction, and that Home Screen web apps get the browser-app quota tier rather than the smaller embedded-WebView tier — which functionally reduces (but does not eliminate, per F4) reliance on `persist()` for Safari specifically.

**Safari's 7-day script-writable-storage eviction (ITP)**
- WebKit blog, *Full Third-Party Cookie Blocking and More* — https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/ — published 2020-04-09 (accessed 2026-07-30). Introduced the rule: after 7 days of Safari use with no user interaction on a site, all script-writable storage (IndexedDB, service worker registrations, Cache API, localStorage) is deleted; server-set cookies are exempt.
- WebKit blog, *Updates to Storage Policy* (as above, 2023-08-10): current framing folds the 7-day rule into the general LRU-by-origin eviction model (last interaction *or* last storage operation), and explicitly states Home Screen/Dock-installed web apps run on their own usage clock separate from Safari-the-browser's, so a user who never opens Safari itself but does open the installed app regularly does not hit the timer.

**IndexedDB reliability**
- MDN, *IDBTransaction: complete event* / *IndexedDB key characteristics and basic terminology* — https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/complete_event and https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Basic_Terminology (accessed 2026-07-30). A transaction auto-commits once all requests placed on it have completed and no new request is placed before control returns to the event loop; a transaction is only "active" within the scope that created it and within callbacks of its own requests — awaiting an unrelated promise mid-transaction lets it close, and subsequent requests throw `TransactionInactiveError`.
- MDN, *IDBTransaction: durability* — https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/durability (accessed 2026-07-30; marked "Baseline 2024 — newly available," i.e. supported in current versions of Chrome, Edge, Firefox, and Safari as of that badge). Three values: `"strict"` (verify persistent-storage write before firing `complete`), `"relaxed"` (fire `complete` once changes reach the OS, not verified flushed to disk), `"default"` (browser's own default for the storage bucket). Neither mode is an absolute guarantee against power-loss data loss — `strict` only narrows the vulnerable window.
- Chrome Developers blog, *A change to the default durability mode in IndexedDB* — https://developer.chrome.com/blog/indexeddb-durability-mode-now-defaults-to-relaxed — published 2023-11-03 (accessed 2026-07-30). Chrome 121 changed the **default** transaction durability from `strict` to `relaxed`, aligning with Firefox (relaxed by default since Firefox 40) and Safari.
- MDN, *WorkerGlobalScope: indexedDB* / *Using Service Workers* — https://developer.mozilla.org/en-US/docs/Web/API/WorkerGlobalScope/indexedDB and https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers (accessed 2026-07-30). IndexedDB is available in both dedicated Web Workers and Service Workers (unlike synchronous `localStorage`, which is not available in any worker context).
- MDN, *The structured clone algorithm* — https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Structured_clone_algorithm (accessed 2026-07-30). IndexedDB values must be structured-clonable: objects, arrays, primitives, `Date`, `Map`, `Set`, `Blob`, `File`, `ArrayBuffer`/typed arrays are supported; functions and DOM nodes throw `DataCloneError`.
- Safari-specific quirks still cited by current sources (e.g., Dexie.js's maintained *IndexedDB on Safari* compatibility notes, and a documented iOS 17.4 regression where existing IndexedDB connections closed with `UnknownError: Connection to Indexed Database server lost` and could not be reopened) — treat Safari IndexedDB as the browser most likely to need defensive reconnect/retry logic in the repository layer, on top of the quota/eviction differences already covered.
- Firefox Private Browsing + IndexedDB: historically disabled (`InvalidStateError` on `open()`, tracked in Mozilla bug 781982), but **Firefox 115 (released 2023-07-04)** shipped IndexedDB support in Private Browsing windows via encrypted on-disk storage with in-memory-only decryption keys, purged at normal session end. Treat pre-115 Firefox as F6 above; 115+ works but is still session-scoped by design.

**Service worker update lifecycle**
- MDN, *ServiceWorkerRegistration: update() method* and *ServiceWorkerRegistration: updateViaCache property* — https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/update and https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/updateViaCache (accessed 2026-07-30). The registration's script-update check bypasses HTTP cache once 24 hours (86,400s) have elapsed since the last check, regardless of `Cache-Control`; a new worker installs only if it is byte-for-byte different from the current one. `updateViaCache` has three values — `imports` (default: HTTP cache never consulted for the SW script itself, but is consulted for `importScripts()` resources), `all` (cache consulted for both), `none` (cache never consulted for either).
- web.dev, *The service worker lifecycle* — https://web.dev/articles/service-worker-lifecycle — last updated 2016-09-29 (accessed 2026-07-30; old but the install/waiting/activate mechanics it documents are unchanged spec behavior). `install` → `waitUntil()` promise must resolve or the SW is discarded; a successfully-installed worker enters `waiting` until the previously-active worker controls zero clients; `activate` fires once the old worker is gone. `self.skipWaiting()` skips the *waiting* phase only (not installing); `clients.claim()` lets an activated worker take control of already-open, uncontrolled clients — Jake Archibald's own guidance (cited via this article and his other writing) is that `clients.claim()` mainly matters for first-ever page loads and can otherwise cause a page to receive responses from a worker with different fetch-handling logic than what the page loaded under.
- MDN, *Cache: addAll() method* — https://developer.mozilla.org/en-US/docs/Web/API/Cache/addAll (accessed 2026-07-30). `cache.addAll()` is atomic: if any one request in the batch fails (network error, non-OK response per spec sensitivity, or a duplicate/overwrite conflict within the same call), the entire call rejects and **no** entries from that call are written to the cache.

**Cache Storage API eviction vs quota**
- MDN, *Storage quotas and eviction criteria* (as above). IndexedDB and Cache API data for an origin live in the same storage "bucket" and share one quota and one eviction decision — the browser cannot evict one and keep the other for a given origin; eviction (LRU-by-origin, or full wipe under Safari's ITP timer) always takes everything in that bucket at once.

**Private-browsing behaviors**
- Chrome Incognito: reduced quota, commonly cited around 5% of disk (or a small fixed cap such as ~300 MB when "clear cookies on close" is set), data cleared at window close — per web.dev *Storage for the web* (2024-09-23) as cited above.
- Firefox Private Browsing: `localStorage` behaves like `sessionStorage` (available, but cleared when the private window closes); IndexedDB now available (Firefox 115+, encrypted, purged at session end) as detailed above.
- Safari Private Browsing: no MDN/webkit.org page found asserting IndexedDB is disabled outright in Safari Private Browsing (unlike Firefox's historical stance); treat Safari private windows as ephemeral-but-functional and still subject to the same structured-clone/quota rules, just session-scoped.

## 3. Recommendation

**IndexedDB repository design**
1. **Atomic write pattern.** Build the full record (or batch of records) as plain structured-clonable data *before* opening any transaction (F12). Open one `readwrite` transaction, fire all `put()`/`add()` calls synchronously against it with no `await` on anything other than the IDB requests themselves (F10), and rely on `IDBTransaction.oncomplete` — not a per-request success callback — as the actual "saved" signal. Wrap every request and the transaction's `onerror`/`onabort` in explicit `QuotaExceededError` handling (F1) that surfaces a user-visible "storage full" state rather than swallowing the error the way `js/store.js`'s `set()` intentionally does for prefs.
2. **Durability as an explicit per-write choice, not a global default.** Expose a repository-level option (e.g. `save(record, { durability: 'strict' | 'relaxed' })`) rather than relying on the browser default, which is `relaxed` on all three engines as of Chrome 121 (F11). Use `'strict'` only for the writes where losing the last few seconds actually matters (e.g., marking a flight log complete, finalizing an exported brief) — default everything else to `'relaxed'` for responsiveness, since `'strict'` still isn't an absolute crash guarantee.
3. **Safari reconnect handling.** Because Safari IndexedDB has a track record of connections dying under it (e.g. the iOS 17.4 `UnknownError: Connection to Indexed Database server lost` regression, alongside its narrower feature support such as single-object-store transactions), the repository layer's `open()` wrapper should detect a dead/errored connection and transparently reopen rather than surfacing a hard failure to the UI on the first hiccup.
4. **Don't rely on private-mode behavior at all.** Since Firefox only gained IndexedDB support in Private Browsing in 2023 (115+) and it's still purged at session end everywhere, don't special-case detection of private mode (unreliable anyway) — just design every write path to degrade to "this session's data may not survive a close" without crashing, and make sure the export/backup path below is reachable at any time, not just at "normal" app exit.

**Backup/export guidance**
5. Because eviction is all-or-nothing per origin (F3, F4, F14) and there is no portable way to detect it before it happens, ship a manual **export mission bundle** action (e.g., serialize mission doc + snapshots to a downloadable JSON/zip) and a matching **import** path, and surface it prominently — this is the actual data-loss backstop, not `persist()`. Treat `navigator.storage.persist()` (see below) as risk *reduction*, and export as the risk *elimination* the offline promise actually depends on.
6. Given the README/`sw.js` framing that this app is "no login, no server-session," the export format should be self-contained (no server round-trip required) so it works fully offline at a trailhead.

**`persist()` request timing**
7. Call `navigator.storage.persist()` once, on first creation of a mission document (a real user action, not on page load) — Chrome/Edge auto-grant based on engagement heuristics that a first-save action helps satisfy, Firefox will show its own permission prompt at that point which is a reasonable moment to interrupt the user, and Safari's own quota tiers make the call low-cost even where it's a no-op. Do not call it on every launch; check `navigator.storage.persisted()` first and only call `persist()` when it's `false`.
8. In onboarding/README copy, explicitly recommend "Add to Home Screen" for iOS/Safari users (F4) — this is the one Safari-specific mitigation with no code involved, since it moves the origin out of Safari-the-browser's 7-day interaction timer and into the app's own usage clock, and it also grants the larger "browser app" quota tier instead of the embedded-WebView tier.

**Service worker update design**
9. Keep the current `sw.js` pattern (`skipWaiting()` on install, `clients.claim()` on activate, default `updateViaCache: 'imports'` by omission) — it already matches the documented safe pattern for a no-server-session app that wants every online visit to pick up the latest deploy (F8, F9). The one thing to add when IndexedDB schema versioning lands: any schema migration triggered in the SW `activate` handler or app startup must tolerate a brief window where both an old and a new tab/client are alive simultaneously post-`clients.claim()` — make schema changes additive (new object stores/indexes, not destructive renames) within a single deployed version.
10. Preserve `cache.addAll()`'s atomicity (F7) for the app-shell precache — don't refactor to a per-file loop that could leave a half-updated shell if one asset 404s.

## 4. Decision impact

- **Confirms the planned split is correct**: small prefs (map view, theme, session flags) belong in `localStorage` (5–10 MiB cap, synchronous, fine for tiny values); mission documents and forecast/terrain snapshots — which can be large and must survive being the *only* copy in the field — need IndexedDB's larger quota and structured-clone support for binary/blob data, not `localStorage`.
- **`persist()` is necessary but not sufficient.** Every browser's persistence model still allows total loss (declined persist request, Safari's ITP timer for non-Home-Screen users, private-mode sessions) — the design must ship an explicit export/import path as the actual offline-durability guarantee, not treat `persist()` + IndexedDB as "safe storage."
- **Safari/iOS is the long pole.** Between the 7-day ITP eviction (mitigated only by Home Screen installation), historically narrower IndexedDB feature support, and a real-world connection-drop regression (iOS 17.4), the repository layer needs Safari-specific defensiveness (reconnect-on-error) that Chrome/Firefox don't require, and product copy should actively steer iOS users toward "Add to Home Screen."
- **No code changes required to `sw.js`'s update lifecycle** — its existing `skipWaiting`/`clients.claim`/atomic-`addAll` pattern already matches the documented-safe approach; the only new constraint the IndexedDB work adds is that future schema migrations must be additive to survive the old/new-client overlap window `clients.claim()` creates.
- **Durability should be a per-call parameter in the new repository's API surface**, not left to browser defaults — this is a small API-design decision now, before call sites multiply, that avoids a larger refactor later to add "important vs. routine write" distinctions.
