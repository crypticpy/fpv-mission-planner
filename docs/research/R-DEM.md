# R-DEM — DEM & elevation-source provider matrix

Research task R-DEM (see `research/AI_AGENT_DEVELOPMENT_PLAN.md` row `R-DEM`). Scope: (a) a raster-DEM tile source for MapLibre 3D terrain, (b) a client-side, CORS-friendly elevation source for route-corridor sampling (hundreds of points per mission), (c) whether bounded offline caching of either is contractually possible.

All claims below were checked against the provider's own primary documentation, or a live `curl`/`WebFetch` against the provider's own endpoint, on **2026-07-30** (dates noted per claim; re-check before relying on this for a license decision more than a few months old — Nextzen and MapTiler pricing pages especially are the kind of thing that changes).

Current code for context: `js/terrain.js` samples `PROFILE_SAMPLES = 28` points along one bearing via a single keyless Open-Meteo `elevation` call (`js/terrain.js:83-98`); attribution already appears in the rendered note as `Elevation data: Open-Meteo (Copernicus DEM)` (`js/render/terrain.js:324`). No MapLibre code exists yet — Leaflet is the only map today (`js/map.js`).

## Decode formulas (primary source: `tilezen/joerd` `docs/formats.md`, and Mapbox's own Terrain-RGB v1 reference)

**Terrarium** (used by AWS Terrain Tiles, Nextzen; MapLibre's `"encoding": "terrarium"`):
```
elevation_m = (red * 256 + green + blue / 256) - 32768
```
Range −11,000 m to 8,900 m; red = 256s place, green = 1s place, blue = fractional (1/256 steps). No official "meters per unit" ambiguity — it's a signed integer-plus-fraction scheme with a fixed +32768 offset, unlike Mapbox's scaled scheme below.

**Mapbox Terrain-RGB** (a.k.a. "mapbox" encoding — MapLibre's default for `raster-dem`, and what MapTiler's default `terrain-rgb-v2` emits):
```
elevation_m = -10000 + (red * 256 * 256 + green * 256 + blue) * 0.1
```
Range roughly −10,000 m to +8,388,600 m in 0.1 m steps; zoom 15 is Mapbox's stated ceiling for added resolution.

Practical note: MapLibre's own `raster-dem` source spec (`maplibre.org/maplibre-style-spec/sources/#raster-dem`, checked 2026-07-30) supports exactly these two named encodings (`terrarium`, `mapbox`) plus a fully custom one via `redFactor`/`greenFactor`/`blueFactor`/`baseShift` (JS-only as of MapLibre GL JS 3.4.0, not yet in the native SDKs — irrelevant here since this is a web PWA). It defaults to `"mapbox"`, so an AWS Terrarium source **must** set `"encoding": "terrarium"` explicitly or every elevation will decode wrong.

## Recommendation

**3D basemap terrain (MapLibre `raster-dem` source): AWS Terrain Tiles, Terrarium encoding, `https://s3.amazonaws.com/elevation-tiles-prod/terrarium/{z}/{x}/{y}.png`.**
No key, CORS-open (verified live), free, and it's literally the dataset MapLibre's own docs point to as the reference example for `raster-dem`. The only cost is an attribution line — a mix of US-public-domain and a handful of CC-BY/open-government regional sources, all satisfied by one static credit list (already have a precedent for this pattern in `js/map.js:61-65`, which carries Esri/OSM attribution strings today).

**Route-corridor sampling (hundreds of points, client-side): keep Open-Meteo, just call it more.**
It already clears every requirement in scope (b): CORS-open, keyless for non-commercial use, JSON (no pixel-decoding needed), 300k calls/day free tier, and it's already wired into `js/terrain.js`. The one real constraint is the **100-coordinates-per-request cap** — "hundreds of points" means batching into ⌈n/100⌉ parallel/sequential requests rather than one call, which is a small, additive change to `fetchElevationProfile()`, not a provider swap. OpenTopography was the other CORS-clean candidate but its 50 calls/24h (non-academic, keyed) budget cannot survive real usage from a public client-side app sharing one key, and per-user key provisioning is out of scope for a static PWA.

**Should 3D-terrain and corridor-sampling be the same provider? Not necessarily, and not today** — but flag the option. AWS Terrarium tiles could, in principle, also answer corridor queries: fetch the handful of covering tiles for a route, decode the Terrarium PNG pixels client-side (canvas `getImageData`), and read elevation at arbitrary points with no per-request cap and no dependence on Open-Meteo staying up. That would unify both needs on one dataset and one license, and — because the tiles are public-domain-heavy and contractually cacheable (unlike MapTiler) — it's also the only path that gets you real bounded *offline* corridor sampling once tiles are pre-fetched. It's more implementation work than the task needs right now (tile math, canvas decode, a small in-memory/IndexedDB tile cache) for a resolution/rate-limit problem that doesn't exist yet at "hundreds of points per mission." Recommend keeping it as the documented upgrade path, not building it now.

**What the terrain-provider port must abstract**, so this doesn't get re-litigated per provider swap:
1. Two distinct capabilities behind one seam (mirroring how `js/terrain.js` is already the only file that talks to an elevation source): a **`TileSource`** shape (url template, `encoding`, min/maxzoom, attribution string) for the 3D basemap, and an **`ElevationSampler`** shape (an async `(coords) => elevM[]` with its own batch-size limit, CORS/auth needs, and attribution string) for corridor sampling. Different providers can fill either slot independently.
2. A **per-provider attribution string** carried as data, not hardcoded prose — Copernicus's license mandates an *exact* notice, AWS Terrarium's is a regional list, Open-Meteo wants CC-BY + a DOI citation. The port should return "here is the credit text this provider requires" so the render layer (`js/render/terrain.js:324` already does something like this for Open-Meteo) can display whichever is active.
3. A **cache-permission flag** per provider — not every source that's technically fetchable is legally cacheable offline (MapTiler's ToS bans it outright; Copernicus's raw COGs are legally cacheable but practically CORS-blocked). The port shouldn't let requirement (c)'s bounded offline cache accidentally get wired to a provider whose terms forbid it.
4. The same degrade-to-last-good-data philosophy `js/terrain.js` already uses (throw on bad payload, caller keeps yesterday's profile) — this should stay provider-agnostic, since batch caps and rate limits (Open-Meteo's 100/request, OpenTopography's 50/day) are exactly the kind of thing that should fail soft, not crash the plan.

## Decision impact

- **No corridor-sampling provider change is needed** — Open-Meteo stays, `PROFILE_SAMPLES` can go from 28 to "hundreds" by batching ≤100-coordinate requests, not by switching providers.
- **Adds a new provider for the 3D basemap**: AWS `elevation-tiles-prod` Terrarium tiles, zero cost, zero key management, matches MapLibre's own documented pattern — this is new surface area for the terrain-provider port, not a replacement of anything existing.
- **Rules out MapTiler as the default/shipped 3D DEM source** specifically because its ToS bans the server-side/bulk caching this project's requirement (c) asks for; keep it only as an optional paid, user-supplied-key upgrade (higher-detail regional data) behind a settings toggle, never the default.
- **Rules out the Nextzen hosted tile service entirely** — confirmed closed to new signups; depending on it would mean shipping a feature on a provider whose own docs say not to. Use the AWS S3 bucket (the same underlying dataset) instead.
- **Rules out OpenTopography for the automatic per-plan sampling hot path** — its 50 calls/24h non-academic budget can't carry real traffic from a shared client-side key. Keep it in reserve as an optional, explicitly user-triggered "fetch research-grade elevation for this one flight" action (also useful later for R-VALIDATION ground-truth fixtures), not the default sampler.
- **USGS 3DEP EPT is out of scope for client-side corridor sampling** — it's a LAZ point-cloud octree meant for PDAL/desktop GIS consumption, not a lightweight point-elevation query; note it as the future authoritative 1 m US-only upgrade path if/when R-VALIDATION needs ground truth to check the 90 m Open-Meteo profile against.
- **Bounded offline caching (requirement c) is contractually clean for AWS Terrarium, Open-Meteo, and USGS 3DEP** (public-domain/CC-BY, no caching prohibition); **contractually blocked for MapTiler** (explicit ToS ban) and **moot for raw Copernicus COGs** (no CORS without a proxy) and **moot for Nextzen** (can't get a key). Any offline-cache design should key its retention policy off this per-provider flag rather than assuming "if it's fetchable, it's cacheable."
