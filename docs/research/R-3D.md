# R-3D — MapLibre GL JS + deck.gl feasibility for a terrain-aware 3D mission scene

Status: research complete, feeds ADR 0004 (`docs/adr/0004-map-adapter.md`).
All facts below were checked against official primary sources only
(maplibre.org docs/examples, github.com/maplibre, deck.gl.org docs,
github.com/visgl, npm registry package metadata, and direct `unpkg.com`
dist-file downloads for size measurement). Date checked for every claim:
**2026-07-30**, unless a different check date is noted inline.

## 1. MapLibre GL JS

- Current stable is **v6.0.0**, released 2026-07-22, confirmed via the GitHub Releases API (`api.github.com/repos/maplibre/maplibre-gl-js/releases`) and the npm registry (`dist-tags.latest = 6.0.0`, published 2026-07-22T16:15Z). License field in `package.json` and npm metadata: `BSD-3-Clause`.
  Source: https://github.com/maplibre/maplibre-gl-js/releases, https://www.npmjs.com/package/maplibre-gl — checked 2026-07-30.
- v6 is an **ESM-only distribution**: "Switch to an ESM-only distribution (`maplibre-gl.mjs`). The UMD bundles (`maplibre-gl.js`, `maplibre-gl-csp.js`) are no longer published." `package.json` exports only `import: "./dist/maplibre-gl.mjs"` (no `main`/UMD entry).
  Source: `CHANGELOG.md` (main branch) and `docs/guides/v5-to-v6-migration-guide.md`, both in github.com/maplibre/maplibre-gl-js — checked 2026-07-30.
- Bundle size measured directly (not from a third-party bundle-size site): downloaded `https://unpkg.com/maplibre-gl@6.0.0/dist/maplibre-gl.mjs` (564,301 bytes) and gzip'd it locally → **141,903 bytes (~138.6 KiB) gzip**. The companion CSS is 70,024 bytes raw / 10,153 bytes gzip. This is the whole library — MapLibre does not ship a smaller "core" tier.
- **WebGL2 is now a hard requirement**: "WebGL (v1) support has been removed; WebGL2 is now required... This enables performance improvements (e.g. line opacity), Terrain3D enhancements, and several bug fixes... To ease this breaking change, we have also refactored how we handle the case that no webgl is available... You can now listen to the webgl error via `.on("error")`." No pre-flight `supported()` static function exists in the current API surface (I checked the full exported-functions list at `https://maplibre.org/maplibre-gl-js/docs/API/` — no `supported`/`isSupported` export). The only documented pattern is reactive: attempt `new Map(...)` and listen for the `error` event, checking `e.error instanceof maplibregl.GPUInitializationError`.
  Source: `CHANGELOG.md` 6.0.0 section; https://maplibre.org/maplibre-gl-js/docs/examples/check-if-webgl-is-supported/ — checked 2026-07-30.
- **Terrain API**: `Map.setTerrain(terrain: TerrainSpecification | null, options?): this`, `Map.getTerrain(): TerrainSpecification | null`, `Map.queryTerrainElevation(lngLat: LngLatLike): number | null`. `TerrainSpecification` = `{source: <raster-dem source id>, exaggeration?: number}`. The official 3D-terrain example uses `exaggeration: 1` (i.e. no vertical exaggeration) as its working default.
  Source: https://maplibre.org/maplibre-gl-js/docs/API/classes/Map/, https://maplibre.org/maplibre-gl-js/docs/examples/3d-terrain/ — checked 2026-07-30.
- **raster-dem encodings**: the style spec's `raster-dem` source supports `encoding: "mapbox"` (Mapbox Terrain-RGB, default), `"terrarium"` (Mapzen/Terrarium PNG), or `"custom"` (`redFactor`/`greenFactor`/`blueFactor`/`baseShift` decode formula). "A raster DEM source. Only supports Mapbox Terrain RGB and Mapzen Terrarium tiles" (plus custom decode).
  Source: https://maplibre.org/maplibre-style-spec/sources/ — checked 2026-07-30.
- **Terrain works with vector or raster basemaps**: MapLibre's terrain is a render-to-texture pass over the *entire style*, not a raster-only feature — "every map feature works seamlessly with the new 3D terrain option: existing layer types are automatically adjusted and aligned with terrain, and markers clamp to the ground." The v6 changelog independently confirms this mechanism ("terrain render to texture", "terrain cache render to texture", "DEM texture reuse") as an internal renderer pass applied uniformly to style layers, not a per-source-type feature. The official 3D-terrain example itself happens to use a raster OSM basemap, but nothing in the terrain pipeline is raster-specific.
  Source: MapTiler's MapLibre v2 announcement (quoting MapLibre's own release notes) + `CHANGELOG.md` terrain entries — checked 2026-07-30. Treat the "vector basemap + terrain" claim as **high-confidence but not directly demonstrated in an official vector-basemap example** — worth a 10-minute spike check, not a full research cycle.

## 2. deck.gl

- Current stable is **v9.3.7**, published 2026-07-16 (npm `dist-tags.latest`). A `9.4.0-alpha.2` pre-release exists (2026-07-29) — do not pin to it. License: `MIT` (npm `package.json`). `@deck.gl/mapbox` (the MapboxOverlay module) is version-locked in lockstep, `peerDependencies: {"@deck.gl/core": "~9.3.0", "@luma.gl/core": "~9.3.3", "@math.gl/web-mercator": "^4.1.0"}`.
  Source: https://registry.npmjs.org/deck.gl, https://registry.npmjs.org/@deck.gl/mapbox — checked 2026-07-30.
- **Bundle size** is only meaningfully documented as an official incremental table (deck.gl is modular by design, not a single bundle): "Deck + Layer" (minimal core) = 501.2 KB / **145.3 KB gzip** baseline; adding `GeoJsonLayer` (which pulls in `PathLayer`, `ScatterplotLayer`, `IconLayer`, `TextLayer`, `PolygonLayer`) = +97.9 KB / +27.7 KB gzip; `MVTLayer` = +180.9/+52.6 KB; `Tile3DLayer` = +253.9/+75.1 KB. Numbers "measured using v9.0.1," bundled/minified by esbuild, gzip -9. There is no official published incremental number for `@deck.gl/mapbox` or `@deck.gl/extensions` (TerrainExtension) specifically — a spike must measure the real total for the exact layer set (likely core + mapbox + a path/geojson layer + extensions + geo-layers ≈ 190–240 KB gzip, unverified estimate).
  Source: https://deck.gl/docs/developer-guide/building-apps (mirrored at `docs/developer-guide/building-apps.md` in github.com/visgl/deck.gl) — checked 2026-07-30.
- **Integration modes with MapLibre** (`@deck.gl/mapbox`'s `MapboxOverlay`), quoting the official guide directly:
  - **Interleaved** (`new MapboxOverlay({interleaved: true, ...})`): "renders deck.gl layers into the WebGL2 context created by MapLibre. If you need to mix deck.gl layers with MapLibre layers, e.g. having deck.gl surfaces below text labels, or objects occluding each other correctly in 3D, then you have to use this option." Requires WebGL2 and "only works with `maplibre-gl@>3`." Layers are grouped and ordered via `beforeId`/`slot`.
  - **Overlaid** (default): renders deck.gl in "a separate canvas inside the MapLibre's controls container." Preferred when you want MapLibre controls/plugins (`NavigationControl`, `Popup`, `mapbox-gl-draw`) but don't need cross-renderer occlusion. deck.gl content always draws on top of the base map as a separate compositing layer — no shared depth buffer with MapLibre's 3D terrain/buildings.
  - **Reverse-controlled**: deck.gl owns the canvas and pointer input; "You cannot use maplibre-gl controls and plugins with this option." For custom input handling or multiple maps.
  Source: https://deck.gl/docs/developer-guide/base-maps/using-with-maplibre (mirrored on GitHub) — checked 2026-07-30. **The official guide does not mention terrain interaction in any of the three modes** — occlusion-with-terrain is not directly documented there; see §3.

## 3. Explicit-elevation limitation, TerrainExtension, and occlusion

This is the crux finding for the ADR 0004 spike gate.

- deck.gl's own RFC (#7195, "Fitting data on terrain surface") states the root problem plainly: **"deck.gl always treats the z component of a geospatial position as altitude,"** which causes (a) 2D layers occluded by a co-present `TerrainLayer`, (b) misalignment when overlaid on Mapbox/MapLibre/Google 3D terrain, and (c) occlusion problems when interleaved with base-map features. This RFC is the origin of `TerrainExtension`; the issue is closed (feature shipped), not abandoned.
  Source: https://github.com/visgl/deck.gl/issues/7195 — checked 2026-07-30.
- `TerrainExtension` is still marked **experimental**: "does not provide the compatibility and stability that one would typically expect from other features." It requires a dedicated terrain-source layer (typically a `TerrainLayer` or `Tile3DLayer`) marked `operation: 'terrain'` (invisible elevation source) or `'terrain+draw'` (visible + elevation source) — **this is a deck.gl-internal 3D surface, separate from MapLibre's own terrain render-to-texture pipeline.** To make a deck.gl layer conform to the same terrain MapLibre is already showing, you load a *second*, typically invisible, deck.gl `TerrainLayer` against the same `raster-dem` tiles.
- `TerrainExtension` has exactly two draw modes, neither of which is "compare my explicit MSL Z against the ground for correct occlusion, without changing it":
  - `drape`: "Overlays the layer as a texture over the terrain surface. All altitude and extrusion in the layer will be ignored." (explicit Z is discarded)
  - `offset`: "translates each object vertically by the elevation at its anchor" — i.e. adds ground elevation on top of whatever Z the object already has (correct for ground-relative height, not for absolute MSL values you want tested against the ground, since it would double-count).
- The most directly relevant sentence for our use case, from the official "Using with 3D Tiles" guide's "Overlaid Layers (non-draped)" section: **"Not all layers need to conform to the terrain. Layers without the `TerrainExtension` will render in their own coordinate space as usual. This is useful for ... data that has its own elevation values."** This confirms: a route/PathLayer carrying explicit MSL-altitude vertices, left alone (no `TerrainExtension`), renders at that raw Z in its own coordinate space — full stop. **No official example demonstrates the exact "hide the route behind a ridge without draping or offsetting it" case.** Whether ordinary GPU depth-testing in **interleaved** mode is sufficient (MapLibre's terrain fragments and the deck.gl path both land in the same WebGL2 depth buffer, at their true projected depths, so nearer terrain naturally occludes a farther path) is asserted by the interleaved-mode description in §2 ("objects occluding each other correctly in 3D") but is not spelled out for the terrain-specific case in any example we found.
  Source: https://github.com/visgl/deck.gl/blob/master/docs/api-reference/extensions/terrain-extension.md, https://github.com/visgl/deck.gl/blob/master/docs/developer-guide/base-maps/using-with-3d-tiles.md — checked 2026-07-30.
- **This is exactly what the ADR 0004 spike must prove in code**, not just in docs: with `MapboxOverlay({interleaved: true})`, a MapLibre `raster-dem` terrain active via `setTerrain`, and a `PathLayer` at explicit MSL Z (no `TerrainExtension` applied), does a ridge in MapLibre's terrain correctly hide the far side of the route? The docs give reason to expect yes (shared WebGL2 context + depth buffer, interleaved mode literally exists for "objects occluding each other correctly in 3D") but no worked example confirms it specifically against MapLibre-rendered terrain (as opposed to a deck.gl-internal `TerrainLayer`/`Tile3DLayer`).

## 4. Picking on terrain-enabled maps

- MapLibre: `Map.queryTerrainElevation(lngLat): number | null` returns ground elevation at a coordinate. This is independent of deck.gl picking — there is no shared API between the two libraries for "what's under the cursor including elevation."
  Source: https://maplibre.org/maplibre-gl-js/docs/API/classes/Map/ — checked 2026-07-30.
- deck.gl: `deck.pickObject({x, y, radius, layerIds, unproject3D})` returns "the closest pickable and visible object at the given screen coordinate"; `unproject3D: true` makes `info.coordinate` "a 3D point by unprojecting the x, y screen coordinates onto the picked geometry" — this is how you'd get an accurate 3D point (including elevation) for a click on a route or terrain-draped layer. `deck.pickMultipleObjects({...,depth})` deep-picks through occluded objects (default depth 10; documented perf cost). Neither method is documented as compatible with the WebGPU backend.
  Source: https://deck.gl/docs/api-reference/core/deck — checked 2026-07-30.
- Terrain-aware camera/picking specifically requires `pickable: '3d'` on whichever layer is the terrain source (`TerrainLayer`/`Tile3DLayer` with `operation` including `'terrain'`): "This enables depth picking on the tileset, which is required for the `TerrainController` to determine the terrain elevation under the camera and pointer... Without a `pickable: '3d'` layer in the scene, the controller has no elevation data and will behave like a standard `MapController`."
  Source: https://github.com/visgl/deck.gl/blob/master/docs/developer-guide/base-maps/using-with-3d-tiles.md — checked 2026-07-30.

## 5. Feasibility without a bundler vs. with Vite

- **MapLibre v6 is straightforward without a bundler.** It's ESM-only, and the official migration guide gives the exact no-bundler pattern: `<script type="module">import * as maplibregl from 'https://unpkg.com/maplibre-gl@^6.0.0/dist/maplibre-gl.mjs';</script>` (or self-host the `.mjs`/`.css` files, matching the project's existing `vendor/leaflet/leaflet-src.esm.js` pattern). The worker URL is auto-detected from `import.meta.url` and laundered through a same-origin Blob URL — no `setWorkerUrl()` call needed for the raw-browser-ESM case. Only a CSP note applies: cross-origin CDN loading needs `worker-src 'self' blob:`; self-hosting (this project's pattern) does not need `blob:` at all. **With Vite**, the same import works, but `import.meta.url` doesn't reliably resolve inside a bundler's module graph, so one `setWorkerUrl()` call becomes necessary per the migration guide's bundler section.
  Source: `docs/guides/v5-to-v6-migration-guide.md`, github.com/maplibre/maplibre-gl-js — checked 2026-07-30.
- **deck.gl is weaker without a bundler.** The only documented non-bundler path is the pre-bundled UMD scripts per module (`<script src="https://unpkg.com/deck.gl@^9.0.0/dist.min.js">`, or narrower ones like `@deck.gl/core`, `@deck.gl/extensions`), which "bundle code with dependencies" targeting `['chrome110','firefox110','safari15']` and are **not tree-shakable** — you pay for the whole module regardless of which layers/extensions you actually use, and they attach to a global `deck` namespace (e.g. `new deck._TerrainExtension()`) rather than clean ESM imports. Since v9.0, "deck.gl is fully ES module compliant with support for both ESM-style `import` and CommonJS-style `require()`" — but the tree-shaking benefit only applies to the `dist/index.js` ESM entry consumed by a bundler; using it via a bare `<script type="module">` + bare specifier `import` without an import map or bundler does not work out of the box, because `import 'deck.gl'` (or `'@deck.gl/core'`) is a bare module specifier that browsers can't resolve without either a bundler or an import map pointing at a CDN URL.
  Source: `docs/developer-guide/building-apps.md`, github.com/visgl/deck.gl — checked 2026-07-30.
- Net: MapLibre alone can ship today, no-bundler, as a drop-in next to the existing vendored-ESM Leaflet setup. deck.gl realistically wants Vite (or at least an import map + CDN ESM build, which is not the officially documented path and would need its own verification) to get tree-shaking and clean module syntax — this is a point in favor of sequencing the 3D work after the Vite build lands, not before.

## 6. Fallback story (WebGL2 absence, 2D-only mode)

- MapLibre v6 has **no automatic fallback to 2D or WebGL1** — WebGL1 support was removed outright. The only documented signal is reactive: initialize the `Map`, then listen with `map.on('error', e => { if (e.error instanceof maplibregl.GPUInitializationError) { /* handle */ } })`. There is no pre-flight `maplibregl.supported()` function in the current API (verified: the full exported-function list at the API docs root has no `supported`/`isSupported` export) — an older Mapbox-GL-JS-era static `supported()` check does **not** appear to exist in current MapLibre v6.
  Source: https://maplibre.org/maplibre-gl-js/docs/examples/check-if-webgl-is-supported/, https://maplibre.org/maplibre-gl-js/docs/API/ — checked 2026-07-30.
- Neither MapLibre nor deck.gl documents an official "run this same map in 2D-only mode" toggle — that responsibility is entirely on the consuming app. For this project, that already matches ADR 0004's plan: **feature-detect first** (a synchronous `WebGL2RenderingContext` capability probe, not a MapLibre-provided check, since none is documented) and choose the Leaflet adapter vs. the MapLibre+deck.gl adapter before ever constructing a `Map`, rather than relying on the reactive `GPUInitializationError` path (which only fires after a failed GPU init attempt, and would leave the app in a half-initialized state that has to be torn down and replaced with Leaflet). The reactive `error` listener is still worth wiring as a second line of defense (e.g., context loss after a driver crash mid-session), separate from a pre-flight capability probe.

## Recommendation

- **Integration mode: interleaved (`MapboxOverlay({interleaved: true})`).** Overlaid mode is documented as not participating in cross-renderer occlusion at all ("renders deck.gl in a separate canvas"), which fails the ADR 0004 exit gate outright (route behind a ridge must be hidden). Interleaved is the only mode the docs describe as achieving "objects occluding each other correctly in 3D," and it's a hard requirement, not a nice-to-have, for this product.
- **Versions to pin**: `maplibre-gl@6.0.0` (BSD-3-Clause, ESM-only, WebGL2-only), `deck.gl@9.3.7` / `@deck.gl/core@9.3.7` / `@deck.gl/mapbox@9.3.7` / `@deck.gl/extensions@9.3.7` / `@deck.gl/geo-layers@9.3.7` / `@deck.gl/layers@9.3.7` (all MIT, all peer-locked to `~9.3.x`). Do not pin `9.4.0-alpha.2`.
- **Sequence the Vite migration before the deck.gl integration.** MapLibre alone works fine unbundled (drop-in `.mjs`, same pattern as vendored Leaflet). deck.gl's only officially-documented unbundled path is non-tree-shaken UMD globals, which is a worse footprint and a worse authoring experience than waiting for Vite + real ESM imports.
- **What the spike must still prove in code** (the docs do not settle these):
  1. With `setTerrain` active and `MapboxOverlay({interleaved:true})`, does a `PathLayer` at explicit MSL Z (no `TerrainExtension`) get correctly occluded by MapLibre's own rendered terrain on the far side of a ridge — using nothing but ordinary shared-context depth testing? Build a ridge fixture and a valley fixture and check both directions (route in front of ridge visible; route behind ridge hidden).
  2. Whether a duplicate, invisible deck.gl `TerrainLayer` (`operation: 'terrain'`, no `'draw'`) sourced from the same `raster-dem` tiles is actually necessary for correct depth behavior, or whether MapLibre's own terrain fragments in the shared WebGL2 depth buffer are sufficient without any deck.gl-side terrain layer at all. This determines whether terrain tiles get fetched/decoded twice.
  3. Real gzip size for the actual layer set chosen (core + mapbox + a path/line layer + extensions, at minimum) via a Vite production build — the official incremental table stops at GeoJsonLayer/MVTLayer/Tile3DLayer and doesn't cover this exact combination.
  4. Whether `deck.pickObject({unproject3D: true})` returns usable 3D coordinates for hazard/route vertex editing when interleaved with MapLibre terrain, and whether MapLibre's `queryTerrainElevation` needs to be called separately to reconcile ground-truth elevation for snapping (the two APIs are not unified).
  5. A minimal WebGL2-capability probe (feature-detect before construction) plus a wired `GPUInitializationError` listener as defense-in-depth, per §6.

## Decision impact for the map-adapter architecture (ADR 0004)

- **Confirms** the ADR's framing that MapLibre+deck.gl is gated on evidence, not assumed safe: the "zero/explicit elevation sits at its given Z rather than draping" limitation is real, documented by deck.gl's own RFC, and unresolved by `TerrainExtension`'s two modes (`drape` discards altitude; `offset` adds to it) — neither mode is "compare absolute Z to terrain for occlusion." The adapter boundary must not assume deck.gl will "just handle" terrain-relative depth; the layer registry needs an explicit contract for which layers use `TerrainExtension` (draped hazard/constraint overlays) vs. which render at raw explicit Z (the route line itself) and rely on shared-context depth testing.
- **Adds a candidate second terrain load**: if the spike (item 2 above) shows MapLibre's native terrain depth is *not* sufficient for deck.gl-side occlusion/picking, the map-adapter will need to own loading the same `raster-dem` tiles twice — once for MapLibre's `setTerrain`, once for a deck.gl-internal `TerrainLayer` — which is a real architectural cost (double DEM fetch/decode) the ADR should budget for explicitly rather than discover late.
- **Confirms the WebGL2 gate is binary and non-negotiable**: both libraries now hard-require WebGL2 (MapLibre v6 removed WebGL1; luma.gl v9 dropped it too). ADR 0004's "2D remains the fallback for non-WebGL2 environments" is correct and must be implemented as a pre-flight capability probe in the adapter's factory/selection code, not as a try/catch around `new Map()` — neither library exposes a synchronous pre-flight check of its own (confirmed no `supported()` export in MapLibre v6's API surface), so this probe is the app's responsibility to write and own.
- **Sequencing**: this research is a point in favor of landing the Vite build (already in progress per the project's stated direction) before starting the deck.gl half of the spike — deck.gl's tree-shaking and clean-import story only exists behind a bundler; MapLibre's does not need one.
- **Bundle budget**: expect roughly 140 KB gzip for MapLibre alone, plus a deck.gl footprint that officially starts at 145 KB gzip for core+Layer and grows per layer/extension added (no official number exists yet for the mapbox+extensions+geo-layers combination this project needs) — the spike's real measured number (recommendation item 3) should become the number ADR 0004 cites, not the estimate in this doc.
